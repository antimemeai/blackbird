# Concurrent and durable coding-agent workflows: refreshed source study

2026-10-14. Independent frumentarius report. This is design input, not an adopted dependency or a statement that Blackbird has implemented these behaviors. Read-only source research; no acquired implementation, test, installer, provider, or operator-account call was executed. OpenAI Docs skill was used for the official Codex comparison slice.

**Finding:** the strongest freshly discovered comparator is **Pi Durable**, released with Pi 1.0 on October 1. The earlier Pi dossier describes a materially older product. Pi Durable already combines durable phase tasks, structured ownership/settlement, replay-aware tools, shared-history forks, atomic application documents, hot extension replacement, background compaction, multiplayer observation and deterministic code-mode replay. Blackbird should explicitly exceed that baseline. Parked agents, context forks, task migration, replay checks and descendant invalidation are also present in other studied systems; none is a supportable novelty claim by itself.

The opportunity is to unite these mechanisms with **separate effect uncertainty, revision-bound execution/publication, demand-driven artifact validity, rich joins, hierarchical resource policy, model-editable context with originals and native refit continuity**. That conjunction is a design direction derived from this study. It is not an exhaustive worldwide superiority finding.

## Pi Durable: the comparator that changes the design discussion

The [October 1 announcement](https://earendil.com/posts/pi-durable/) introduces a separate experimental harness, not a replacement for the terminal Pi coding agent. It describes concurrent conversations, typed application documents, background work and clients attaching to committed state. The current [Pi site](https://pi.dev/) still excludes built-in subagents from the terminal product but now includes MCP and code mode; the old "no MCP" description is stale. Treat terminal Pi and Pi Durable as distinct products.

### Real intent and result crash seam

In [`harness/tool.ts`](https://github.com/earendil-works/pi/blob/b45e0ebcc5ae2fc42a6f2f23104d10e656e6bedb/packages/durable/src/harness/tool.ts#L108), the normal `call` phase resolves/validates the tool, runs rewrite/block hooks, then commits final arguments and `phase: execute` with the replay declaration **before** `run()` dispatches. Recovery in `execute` reruns only when both the stored declaration and the currently resolved tool say `safe`. Otherwise it settles a failed task and emits an `interrupted` result saying the tool may have partially run. The result is not fabricated success. Nested calls have independently retained keys/results and belong to the caller's task.

This leaves a conservative ambiguity window between committed intent and actual dispatch, and another between external completion and committed result. There is no separately identified arbitrary external effect reconciliation in the inspected tool kernel. A replay-safe external action still needs its own idempotency. A task containing multiple external actions cannot derive per-action outcomes from one interrupted tool diagnostic.

**Blackbird consequence:** retain this conservative behavior as a minimum, then represent each attempt and effect separately. Distinguish admitted, dispatched where the adapter can confirm it, externally complete, recorded complete and unresolved. Reconciliation needs durable input, original operation identity and adapter-specific query/retry behavior. A terminal task result must not erase its unresolved effects. A model may choose recovery policy, but a new retry must remain visibly a new attempt.

### Structured ownership and durable versions

[`harness/scheduler.ts`](https://github.com/earendil-works/pi/blob/b45e0ebcc5ae2fc42a6f2f23104d10e656e6bedb/packages/durable/src/harness/scheduler.ts#L574) derives abort cascades and finalizes held outcomes. A task remains `completing` until its ordinary owned work ends; failed/aborted outcomes cancel that work. Abort handlers run bottom-up. Background ownership boundaries let work survive ordinary parent abort. Wait policy supports `allSettled` and `failFast`; independent any/quorum policies are not present in the inspected native wait surface.

The same source at lines 1209–1235 resolves a task by kind/version. A newer definition migrates stored input/checkpoint; missing definitions, older installed versions or failed migration block execution. After durable progress the scheduler refreshes the registry and may hand off to a replacement definition. This is real version-aware continuation, not heap serialization.

A cooperative task that never returns after abort can delay harness close, as the [durable README](https://github.com/earendil-works/pi/blob/b45e0ebcc5ae2fc42a6f2f23104d10e656e6bedb/packages/durable/README.md#L694) expressly states. Safe/unsafe tool policy is not process termination proof. One process owns a storage; the README explicitly states no cross-process locking. SQLite uses WAL with NORMAL synchronization and a process-crash guarantee narrower than host/power failure.

**Blackbird consequence:** expose scope result readiness separately from scope settlement and external-effect resolution. Define what a quorum does with losers: drain, cancel and settle, or explicitly transfer to a durable owner. Native process/provider adapters must report their actual stop capability. A detached or unknown remote effect cannot silently become settled. Single-owner local execution is acceptable only when explicitly enforced or guaranteed by lifecycle; remote takeover requires generation fencing, not merely a timer.

### Atomic documents, forks and malleability

[`storage/sqlite/storage.ts`](https://github.com/earendil-works/pi/blob/b45e0ebcc5ae2fc42a6f2f23104d10e656e6bedb/packages/durable/src/storage/sqlite/storage.ts#L175) writes entry/task table changes and document delta actions in the **same database transaction**, then advances commit sequence. This supports atomic internal application state plus transcript publication. It is not an atomic transaction with arbitrary shell/API effects.

[`session/forks.ts`](https://github.com/earendil-works/pi/blob/b45e0ebcc5ae2fc42a6f2f23104d10e656e6bedb/packages/durable/src/session/forks.ts#L28) selects `asOf` documents at the fork entry's commit sequence and `current` documents at the parent's current state, using retained copy sources and rejecting duplicate target addresses. Fresh documents use their definitions. Shared transcript ancestry and document-specific fork policy are already concrete competitor features.

Registry replacement is deliberately malleable: live calls retain their resolved tool object, later calls resolve the new registration, and a restart installs current code by name. Source/version identity of each executable tool is not pinned by the inspected intent record. A same-name, same-`safe` tool replacement can change what recovery executes.

**Blackbird consequence:** retain exact effective program/module/tool identity for each run and attempt. Staged revision applies at the affected-workflow boundary by default; explicit migration must name source and target revisions. A fork selects policies for internal state, artifacts, tasks and unresolved effects individually. It never implies rollback of files or outside actions. Preserve past tool behavior even if current discovery advertises a replacement.

### Deterministic code-mode replay is already shipped

[`codemode/codemode.ts`](https://github.com/earendil-works/pi/blob/b45e0ebcc5ae2fc42a6f2f23104d10e656e6bedb/packages/durable/src/codemode/codemode.ts#L1) restarts QuickJS from retained start data with controlled seed and clock, then redelivers committed results in recorded delivery order. It records issued-call counts before releasing those calls to the host, reattaches keyed nested tasks and checks arguments/target. Module version, VM fingerprint or divergent control flow cause replay rejection. Its own comments acknowledge extra journal/count commits per sequential result. Completed calls are not naively relaunched.

**Blackbird consequence:** a constrained Lua recorded-command replay frontend is sound direction, but not unprecedented. Source-pin it, control every exposed nondeterministic input, verify command identity before dispatch, and report a replay mismatch without launching new work. Measure journal bytes, replay CPU and recovery delay on long programs. Explicit durable segments can avoid repeated-prefix work; replay and segment programs should share task/effect semantics.

## Oh My Pi: agent generations, parking and revival

Fresh Oh My Pi is materially stronger than the September dossier. [`registry/agent-lifecycle.ts`](https://github.com/can1357/oh-my-pi/blob/ce932132ab871488c0678caf6fadfe0a768107d8/packages/coding-agent/src/registry/agent-lifecycle.ts#L1) parks idle sessions while retaining identity/transcript, coalesces concurrent revival, and binds every delayed lifecycle operation to the exact registry ref. A stale release cannot kill a replacement with the same display ID. Cold revival builds a current session from persisted metadata. A failed cold revival drops the poisoned adoption so a later try can use fresher context.

Explicit kill publishes detached `aborted` state and writes a tombstone before returning. [`persisted-agents.ts`](https://github.com/can1357/oh-my-pi/blob/ce932132ab871488c0678caf6fadfe0a768107d8/packages/coding-agent/src/registry/persisted-agents.ts#L778) checks the sidecar, rejects incomplete spawn stubs, and performs an expected-ref check after asynchronous metadata reads. This prevents roster discovery from stealing a concurrently spawned identity or resurrecting killed work.

The inspected [generation-race tests](https://github.com/can1357/oh-my-pi/blob/ce932132ab871488c0678caf6fadfe0a768107d8/packages/coding-agent/test/registry/agent-lifecycle.test.ts) directly exercise delayed release, kill during revival, coalescing, cold retry, and tombstone/dispose races. They were read, not run. The lifecycle implementation logs session dispose/owned-resource cleanup failures while preserving terminal/detached registry state: that row alone does not prove all OS or remote work stopped.

The [task surface](https://github.com/can1357/oh-my-pi/blob/ce932132ab871488c0678caf6fadfe0a768107d8/docs/tools/task.md) supports session-scoped semaphore bounds, async jobs, typed yields, worktree patches, nested outputs and peer messaging. [RPC controls](https://github.com/can1357/oh-my-pi/blob/ce932132ab871488c0678caf6fadfe0a768107d8/docs/rpc.md) distinguish message acceptance from eventual result and expose progress/events, steer and idempotent kill behavior.

**Blackbird consequence:** agent identity needs stable logical ID **and** an incarnation/generation in all message/result/control routes. A late result from an old generation is retained but cannot write current state or satisfy a new join. Persistent roster records require status and restart policy, not just recoverable transcript filenames. Tombstones must block resurrection, while cleanup failures and unresolved effects remain visible. Budget ownership must cover nested fan-out globally; a session semaphore is only one constraint.

## Hermes: independent completion units and uncertain scheduled work

[`delegate_tool_dispatch.py`](https://github.com/NousResearch/hermes-agent/blob/0e427d788d253630d38a3a51cd76849e73cd6925/tools/delegate_tool_dispatch.py#L1) partitions a call into independent background completion units by task group, so one finished group need not wait for the slowest unrelated child. Origin session/wake/steer authority is captured before child construction mutates ambient session bindings. Child futures use a bounded pool and FIRST_COMPLETED polling. Per-child background completion is recorded immediately, but explicitly best-effort: write failure does not propagate into the join.

Parent interruption signals children, then reports pending children interrupted and abandons their daemon workers. The [interrupt/join source test](https://github.com/NousResearch/hermes-agent/blob/0e427d788d253630d38a3a51cd76849e73cd6925/tests/tools/test_delegate_parallel_interrupt_join.py) tests returning despite a wedged child and joining normal completion. This buys responsiveness, not settled cancellation.

[`cron/executions.py`](https://github.com/NousResearch/hermes-agent/blob/0e427d788d253630d38a3a51cd76849e73cd6925/cron/executions.py#L216) records claimed attempts before dispatch, distinguishes handoff adoption/running, and keeps terminal states immutable. Recovery marks dead-owner work `unknown` without scheduling retries. Fresh code additionally marks sufficiently silent **live** external owners unknown, explicitly without killing the process; this can release future schedule admission while old work remains. Progress stamps distinguish healthy long jobs from silent wedges.

**Blackbird consequence:** group completion and durable occurrence identity are valuable. Never equate abandoned worker, reclaimed schedule claim, and externally stopped work. No automatic retry of an ambiguous publication. A live-but-silent worker can lose local publication authority through a fence, but a remote target must honor that fence or its external action remains potentially active. Durable capture failure must prevent advancing a run whose recovery relies on that record.

## LangGraph: per-task recovery inside supersteps

Current [checkpointer documentation](https://docs.langchain.com/oss/python/langgraph/checkpointers) describes a full checkpoint at each superstep plus independently written task outputs. Successful sibling writes are reused when another node fails. Replay from an earlier checkpoint re-executes subsequent nodes, including model/API calls. Durability modes are `exit`, `async` and `sync`, with explicit crash tradeoffs. Beta `DeltaChannel` reduces accumulated channel rewrite costs; it requires current versions and remains an unstable API.

In [`pregel/_runner.py`](https://github.com/langchain-ai/langgraph/blob/53cf85bece131f81408c388a783b3dee2932d80a/libs/langgraph/langgraph/pregel/_runner.py#L576), completion/cancellation/error/interrupt writes are recorded under `task.id`, and even successful tasks with no data receive a completion marker. FIRST_COMPLETED processing emits partial progress before the graph step finishes. Cancelling Python futures is not a general outside-effect rollback.

**Blackbird consequence:** independently persist each child completion; a parent crash while one sibling runs must not lose completed siblings. Use independent task readiness for low-latency continuation, with explicit barriers only where the authored semantics require one. Delta/shared-prefix storage is a baseline, not automatic superiority. Keep replay, recovery and a new fork distinct, especially when replay would publish again.

## Microsoft Agent Framework: logical replay identity under concurrency

The fresh [functional API](https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/functional) uses ordinary async functions, optional tracked `@step`, and agents/workflows with a common interface. `request_info` suspends then re-executes the workflow from its beginning; completed steps return cached results. Graph APIs separately checkpoint executor state/messages/shared state at superstep boundaries; [agent executor docs](https://learn.microsoft.com/en-us/agent-framework/concepts/workflows/advanced/agent-executor) warn that server-side provider session state is not captured and can change after a checkpoint.

[`_functional.py`](https://github.com/microsoft/agent-framework/blob/95feea605dbbe879f678602585c76fdb5a963b63/python/packages/core/agent_framework/_workflows/_functional.py#L304) hashes code/default/closure and canonical argument identity. Repeated automatic identities include occurrence counters; explicit replay keys must be unique. Opaque/captured state needs a supplied versioning contract. Unverifiable concurrent legacy cache hits reject rather than pair results by accidental scheduling order. After a live step returns, it snapshots the result, inserts cache state, emits completion and saves a checkpoint: external completion before that save remains a rerun window.

**Blackbird consequence:** distinguish stable logical operation identity from attempt/order/worker identity. Dynamic fan-out uses explicit semantic keys; simultaneous identical arguments may denote two distinct purchases, test shards or model samples. Retained code and inputs must match recovery; replay must reject mismatches. Stateful provider sessions are outside resources, not data captured merely by storing their IDs. Do not deepcopy every prior result/event into each checkpoint.

## CrewAI: edited-output forks and best-effort checkpoints

The current [checkpoint docs](https://docs.crewai.com/v1.15.28/en/concepts/checkpointing) describe full entity snapshots, lineage-preserving resume and fresh-lineage fork, with completed task reuse. The checkpoint UI lets users edit completed outputs; forking invalidates downstream tasks. Automatic event-driven checkpoint writes are best-effort, while manual writes re-raise. JSON files and SQLite are separate providers. This is stronger than the earlier state-only `@persist` summary.

[`checkpoint_listener.py`](https://github.com/crewAIInc/crewAI/blob/b0c16c162aa34454d77d0f266c2b03aa5a3e5764/lib/crewai/src/crewai/state/checkpoint_listener.py#L232) confirms the automatic listener catches failures and logs a warning. Current [flows docs](https://docs.crewai.com/en/concepts/flows) offer typed shared state, event listeners, routers, multiple starts and nested crews. These docs do not establish arbitrary side-effect exactly-once semantics or automatic external reversal when task output is edited.

**Blackbird consequence:** interactive counterfactual editing belongs in the product. But invalidate against actual dependency/artifact/context inputs rather than assuming all results are ordinary task text. A changed source output may invalidate a report without authorizing a second external publication. Checkpoint write failure must have a defined run state and propagation; do not claim durable success after a warning. Separate cheap materialized state from complete retained originals.

## Gas City and adjacent systems: what breadth adds

Gas City supplies heterogeneous external-agent orchestration, Beads formulas/molecules, work routing, durable waits/mail and controller reconciliation. [`runtime_lease.go`](https://github.com/gastownhall/gascity/blob/2550c900350c28948eafecc4c5318350d28529e1/internal/session/runtime_lease.go#L22) combines a local flock with a store revision/monotonic epoch fence for cross-host startup/stop serialization. It documents clock skew, unsupported cloned live owners and best-effort behavior without conditional store writes. [`actor.go`](https://github.com/gastownhall/gascity/blob/2550c900350c28948eafecc4c5318350d28529e1/internal/session/actor.go#L52) distinguishes operator, agent, background and controller actions; only operator resume consumes an operator hold. [`wait_store.go`](https://github.com/gastownhall/gascity/blob/2550c900350c28948eafecc4c5318350d28529e1/internal/session/wait_store.go#L10) retains durable waits and surfaces partial/capped lookups rather than silently treating them as complete.

**Consequence:** lifecycle serialization, authority provenance, durable waits and explicit partial query results are mature comparator behavior. A Blackbird task handle should work over native participants and external-agent adapters without pretending those adapters can see or stop every outside effect. Blackbird consumes shared compute services; it does not inherit Gas City's fleet control-plane role.

## Comparison workloads that defeat shallow parity

These are proposed direct acceptance workloads, not executed competitor failures. An upstream may implement additional adapters/policies; the table identifies what the examined baseline does not establish. Use semantic outcomes as oracles, then measure actual latency/bytes/CPU for the same workload.

| Workload | Required Blackbird behavior | Why a shallow implementation fails |
| --- | --- | --- |
| **Quorum with a live loser** | Three reviewers yield schema-valid independent findings; the first qualified pair releases synthesis; one still-running reviewer is drained/cancelled/transferred explicitly; scope settles only according to that chosen policy | Returning first two futures silently strands work, spends more money or lets a stale reviewer publish after current revision |
| **Parent crash during heterogeneous fan-out** | Completed child outputs survive independently; unfinished native/provider/external-agent work reattaches or becomes unresolved with real identities | Parent snapshot at batch end loses finished work; conversation resume alone recreates agents without work identity |
| **Two effects in one interrupted tool** | First action completed, second uncertain; retain distinct action identities and reconcile each; retry only what the effect contracts permit | One safe/unsafe flag reruns first action or gives up useful recoverable work |
| **Crash after publication before recorded return** | Restore original publication identity, query target/dedup key, and settle ambiguity; no inferred “failed means never published” | Step cache written after return cannot distinguish published from absent |
| **Changed executable under a safe name** | Original attempt uses retained definition identity; replacement requires staged activation or explicit migration | Recovery resolves current tool by name and executes different code while claiming continuation |
| **Killed worker resurrects with delayed response** | Logical task/generation/attempt fence rejects stale publication but retains the original response; dead generation cannot satisfy a new join | Display-name targeting and transcript rescans revive killed work or attach late output to a replacement |
| **Nested capacity and wait deadlock** | Parent and children share budget lineage; sleeping/awaiting parents release execution capacity; dependency cycles report deterministically; provider concurrency and memory/output backpressure remain bounded | Each child starts its own semaphore, multiplying limits, or parents occupy all permits while awaiting children |
| **Replay order changes** | Source and logical operation keys match; recorded nondeterministic arrivals reproduce decisions; divergence fails before new dispatch | Arrival-order counters bind result A to call B, or a deterministic claim ignores clock/random/tool discovery |
| **Counterfactual output edit after effects** | New branch inherits originals and appropriate state; pure descendants invalidate; prior publications remain visible with explicit fresh-effect policy | UI “rewind” accidentally repeats deployment/email/commit or silently claims it rolled back |
| **Deleted artifact with successful task record** | Cache validates output existence/content/environment and dependencies; recompute only invalid demands; changing capacity does not invalidate semantic work | A success blob substitutes for usable output or mutable environment is omitted from cache key |
| **Paused campaign gets messages during refit** | Durable mailbox/cursor records accept messages; owned work reaches actual quiescence; resume uses same participant/workflow identities and observes staged code activation | UI pause hides live effects; restart loses queued events or steals governance of shared daemons |
| **Large retained history, tiny active workset** | Shared originals and indexed checkpoints; cold history stays on disk; query/paging does not load every payload; resume cost reflects active continuation | Full transcript copies per child/checkpoint or replay from genesis produce quadratic traffic/latency |
| **Capture/checkpoint writer fails** | Stop relevant admission/transition and surface retained failure; completed originals remain inspectable; recovery restores the committed prefix | Best-effort logging lets live state advance beyond what restart can reconstruct |
| **Live-but-silent remote worker** | Lost local ownership revokes acceptance/publication using epochs where supported; target-side actions remain unresolved unless executor truly fences/stops | Expiring a lease is mistaken for terminating a live process or undoing an API effect |

## Design implications to carry into the specification

1. **One task machinery, several programming paradigms.** Native turns, Lua durable segments, restricted replay programs, DAG/statechart/dataflow and external adapters share identities, supervision, effects and queries. A workflow itself is callable as a participant operation. Representational expressibility is insufficient without matching failure behavior.
2. **Separate work, attempts and effects.** Task output success, task settlement, artifact validity and externally resolved effect are separate facts. This is the strongest practical advance beyond the examined agent baselines.
3. **Pin executable meaning.** Retain effective source/modules/tool schema/model/context inputs. Allow policy/resource changes without invalidating semantic results; allow semantic migrations only through an explicit source-to-target transform and retained record. The operator's affected-workflow boundary remains the default.
4. **Make context first-class workflow state.** Branches select original/context views and import bounded findings with ancestry; transforms and repairs remain editable, inspectable and tied to final provider requests. No full history copy per colleague.
5. **Rich joins and independent readiness.** All/any/quorum/first-success/first-complete need distinct eligibility, tie order, impossibility and loser policies. Return ready results quickly while showing actual settlement. A quality predicate is authored workflow policy, not a runtime assertion that the answer is correct.
6. **Incremental demands and artifact lineage.** Track the inputs each unit actually reads; recompute affected descendants, verify external artifacts before reuse, and reserve exclusive publication paths or generation-fence commits. The runtime cannot make arbitrary shared file writes transactional by calling them tasks.
7. **Structured resource ownership.** Budgets, provider lanes, worktree leases, output retention and fairness apply across descendants. Suspend does not consume execution permits; acquiring multiple capacities must have a defined ordering/admission operation. Services remain independently governed.
8. **Model/operator ergonomics are semantic.** The same program can be started from terminal, model or event, detached into standing work and attached for steering with the same identity. Show why it waits, what code/context it uses, which effect is unresolved, and what a control action will reach.
9. **Performance is a design obligation.** Incremental ready queues, retained/shared payloads, batched durable transition writes and indexed active-state recovery belong in the architecture. Compare useful workload completion, p50/p99 scheduling/control latency, bytes per transition and recovery work. Do not substitute an RSS ceiling or periodic certification ceremony for useful measured capability.

These changes are exactly why inherited competitor summaries cannot be treated as current design ceilings.
