# Concurrent and durable workflows: native source inventory

Read-only source archaeology, 2026-10-14. Source base: `64d75fb71a78ea62c471441910a89ce4c8ca1208`, branch `work/workflow-design-2026-10-14`. No product edits, builds, tests or performance trials were performed for this report. Tests below are source-inspected existing oracles, not a fresh pass claim.

## The actual starting point

Blackbird already owns the hard low-level ingredients: a sequential retained-state custodian, native typed identities, atomic retained decisions/invocations/admissions, dispatch consumption, reconciliation fences, immutable originals, checked archive readers, Lua source retention, bounded threaded colleagues, and process jobs with independently observed exit/stream/cleanup state. W1 delivers callable workflows and retained configuration activation. W2–W6 remain design orders, not delivered workflow scheduling.

The central integration constraint is already explicit in [CORE_DESIGN](../../docs/CORE_DESIGN.md): one custodian owns publication; each Lua VM has one execution owner; independently running effects return messages to that owner; the terminal is a client. A design that puts a mutex around `CodingEngine` or lets new workers invoke its methods directly would violate the actual machine's ownership, even if those workers each got a fresh Lua VM.

The October 7 [workflow campaign](../../docs/WORKFLOW_CAMPAIGN.md) establishes the intended capability families. Its timed W0 instructions and allowance are historical. The current source is much more informative than the W0 failure: it exposes where W2/W3 must connect.

## Execution and persistence details that matter

### Current workflow calls are synchronous composition

`CodingEngine::execute_workflow` [retains selection and source](../../src/coding.cpp#L3915), wraps the call as an ordinary admitted `workflow_execute` operation and instantiates `Runtime child{*this}`. The child VM isolates Lua globals/cache but reads and mutates the parent's engine/context. It cannot be moved onto a new thread against that same engine. The child VM does not have a distinct conversation or working-context branch.

`workflow_invoke` [selects and retains the exact definition](../../src/coding.cpp#L4628). If context includes unanswered provider calls, it queues an accepted continuation to preserve valid provider protocol; [drain_workflows](../../src/coding.cpp#L4015) runs it after outputs are closed, before another provider request/successful boundary. The queue is a same-turn protocol workaround, not a durability mechanism. `Running` cleanup [clears it unconditionally](../../src/coding.cpp#L5488).

`program_config` syntax-checks proposed modules/workflows and stages them. [Turn success](../../src/coding.cpp#L5650) writes context plus effective program record in a single durable boundary and swaps configuration only when that record was accepted. Failed/cancelled turns discard pending configuration. This is useful activation machinery, but it currently gates against a single active turn. Concurrent roots require generation applicability/ancestry accounting and pending-root admission closure, as the core design already specifies.

### Existing retained decisions can carry a durable continuation, but current calls do not

[DecisionEvent](../../include/blackbird/retained_events.hpp#L119) has actor, conversation, workflow, generation, context revision, a vector of planned invocation identities and immutable continuation bytes. InvocationEvent retains exact input and its originating decision; AttemptAdmissionEvent separately admits a physical attempt. RetryEvent relates a distinct new attempt to a new decision under the existing logical invocation. These are sound building blocks for segmented durable orchestration.

[CodingEngine::operation](../../src/coding.cpp#L3089) presently issues a new decision, invocation and attempt for every call, retaining all three in one batch. Its continuation bytes describe operation/input binding/revision/generation. They are not a resumable named workflow segment. It assumes one planned invocation in the current application's recovery classifier.

[RetainedState::dispatch](../../src/retained_state.cpp#L2539) checks live publication, current admission, no open/terminal observation and live evidence; commits AttemptOpenEvent before calling the external boundary; then records a receipt. Consequently, a process crash between open and actual dispatch leaves uncertainty even when the effect never occurred. This is intentional consumption-before-call behavior. Recovered admissions never regain dispatch authority. Exact duplicate admissions return existing state and do not repeat effects. Retry requires a new attempt and retained decision, not clearing the old row.

The durable scheduler should adopt these rules directly. It should not invent a separate retry ledger, pretend a missing receipt proves no execution, or rerun arbitrary Lua from its beginning and let `operation` invent fresh identities.

### Existing recovery is conservative acknowledgement, not continuation

[recover_coding_session](../../src/coding.cpp#L2770) validates supported metadata and the exact invocation/input/context/generation links. Its `linked` predicate presently requires `decision->planned_invocations.size() == 1`. Supported provider/participant operations can be acknowledged unknown; local file/process/Lua/workflow unknowns require explicit local-unknown recovery mode. It then records terminal UNKNOWN, preserving uncontained command uncertainty and restart/backstop fences. Unsupported operations refuse.

Do not silently make that classifier treat new workflow checkpoints as old native operation metadata. Implement typed workflow recovery: reconstruct the retained segment/control state, expose live/uncertain effects, reconcile their executor authority and choose only a continuation whose dependencies are settled or whose branch handles uncertainty explicitly.

SavedState [collects unresolved attempts and their transitive decision/invocation closure](../../src/retained_state.cpp#L3030), but supported compact reopening currently requires no unresolved state and no station/pending restart. [current_programs](../../src/retained_state.cpp#L2930) reduces only known program labels: session identity/settings/restart/recovery, station prefixes, participants state, workflow effective config, context budgets and tasks. A new generic program snapshot would be omitted unless reducer support is added. Long waiting workflows must reopen from native workflow projection plus bounded suffix, not full historical replay by accident.

### Participants supply genuine concurrency and limited persistent memory

[start](../../src/participants.cpp#L1003) prepares request, stages registry node and cleanup/capture resources, retains admission original, inserts row and saves snapshot before launching the thread. Worker transport never writes RetainedState; original tickets publish bounded capture nodes for owner drain. [drain](../../src/participants.cpp#L889) retains exact originals and then snapshots state. Overflow retains emergency owned original where possible, requests stop and reports explicit unknown instead of dropping silently. Save/retain failure stops owned workers and leaves retention debt.

Workers can [publish presentation activity](../../src/participants.cpp#L230), so future callback interfaces must retain the current separation: presentation callbacks may be concurrent; business state, context and retained publication may not. The owner reentry guard refuses ordinary controls from Retain/Save/Publish/cancellation callbacks. Mandatory shutdown remains available.

The [worker](../../src/participants.cpp#L585) continues sequential directions on the same thread/request context, transitions to `waiting` when a successful request finishes, and stays live until seal/cancel. [await](../../src/participants.cpp#L1305) waits for finished or waiting with empty inbox and has a caller timeout; timeout does not terminate the participant. [join](../../src/participants.cpp#L1337) seals each selected inbox, waits for all workers to finish, joins and drains. It has no explicit deadline, success predicate, any/quorum selection or loser policy. Calling it to implement a readiness join would accidentally terminate a conversational inbox.

[Restore](../../src/participants.cpp#L829) seals every saved row and marks previously running/waiting/cancel-requested state unknown, removes live request and never calls provider. Message dedup is per resident run: identical message identity/arguments returns duplicate; different payload conflicts. It is not a durable global event inbox, cross-process mailbox or resumable colleague program.

Provider profile currently requires context-only/no tools. Task-local coding/model engines are additional executors, not an already present participant mode.

### Command jobs provide the strongest executor precedent

[COMMAND_JOBS](../../docs/COMMAND_JOBS.md) closely matches actual code. Command identity is original launch attempt. Later wait/input/signal/resize operations have their own admissions. Foreground attachment and process lifetime are different; each wait has an epoch so delayed background controls cannot affect a replacement waiter. The same worker remains process/PTY/stream owner through every wait.

Command state [keeps custody, leader exit, output closure, cleanup and retained terminal distinct](../../src/command_jobs.cpp#L306). Capture queues/tails share immutable chunks. Reads expose retained bytes only. Launch deadline never renews on foreground wait. Sticky stop is separate from observed signal/exit. WNOWAIT pins native child identity until group cleanup; group signals cease after reap. A leader exit cannot certify escaped descendants or pipe EOF. Shutdown wakes stopped/full-queue workers using prepaid cleanup resources.

[poll_commands](../../src/coding.cpp#L2570) alone drains output/terminal into the audit, and [operation](../../src/coding.cpp#L3089) routes controls through ordinary admission. Aggregate settlement reserve protects workflow cancellation plus per-job terminal debt, including after a foreground wait releases. Retention failure sets sticky command failure, stops owned work, and never invents an output locator. Job terminality requires retained terminal result, not just worker return.

Command jobs therefore supply a template for native workflow task executors: prepare all mandatory settlement/cleanup before admission; publish one immutable executor observation queue; track authority and transport/capture/local settlement separately; conserve originals under bounded backpressure; expose control acceptance separately from its observed result.

They do not supply process survival. An independent owned supervisor/custodian must receive launch/control identity and retain its own custody before a surviving executor can be advertised. Saved PID and session lock are insufficient.

### Scheduler fairness is presently incomplete

[Provider cancellation tick](../../src/coding.cpp#L4249), [provider stream callback](../../src/coding.cpp#L4340), [local tools](../../src/coding.cpp#L5243) and [Lua instruction hook](../../src/coding.cpp#L1727) pump command jobs. Participant captures drain explicitly in await/join and at [main idle boundaries](../../src/main.cpp#L1459). A long active main request can delay participant retention even while workers genuinely run.

A new execution owner should drain one fair native inbox covering worker completion/originals, operator controls, timers, feed admission and runnable scripts. Bound work per owner visit; reserve urgent stop/settlement capacity independently. Avoid separate polling loops with incompatible starvation behavior. Raw instrumentation is observation, not this scheduler's command source.

### The existing terminal already transfers sole retained ownership

[Terminal turn dispatch](../../src/terminal.cpp#L1750) registers a worker lane, prepares a [RawRetainedTransfer](../../include/blackbird/raw_retained.hpp#L356), stages held settlement resources before launch, and gives the actual worker a lexical storage handoff. On actual join, it restores the parent owner. [Transfer implementation](../../src/raw_retained.cpp#L666) checks original thread/process, refuses wrong incarnation, and preserves blocked ownership debt if wake rearm/return admission fails. This is exclusive owner transfer, not shared access. A standing scheduler owner can extend this mechanism; concurrent task executors must not each receive competing retained grants.

The UI currently constructs and joins the turn worker, so its physical scheduling loop still contains the owner-transfer mechanics even though UI projection does not write execution state. A persistent native workflow custodian should own long-lived execution independently of any particular attached terminal, with the UI receiving its ordinary projection/control endpoints. This should preserve the existing raw-storage grant/settlement rules rather than bypassing them with a new generic thread pool.

The existing [Lua source study](../2026-10-01-lua-embedding-grounding.md) is directly applicable: coroutine yield stores a `lua_KFunction` and `lua_KContext`, not a C++ stack frame; yielded operations require rooted native state and exact resumed result shape; workers enqueue and a single owner resumes. Current [bridge](../../src/coding.cpp#L1539) roots result/error behind a protected preparation shim and raises only after C++ owners are gone, but does not yield. Adding yield through that synchronous frame requires an owning continuation object, explicit generation pin, and qualification of the actual selected Lua 5.4.8 build. The study's Lua 5.5.1 source was research, not the selected runtime or an implementation claim.

## Proposed owning boundaries

1. **Native workflow custodian, same ledger.** Add native typed workflow/run/scope/task/segment/wait/control transitions and checked reductions to RetainedState. The journal remains authority. Saved projection and indexes reconstruct from it. UI/tasks/trace views consume projections and send admitted controls.
2. **Task-local programming facade.** A task owns its exact generation, Lua state, working-context revision/branch, provider configuration and child scope. The existing engine's shared mutable context/trace pointers cannot remain implicit task globals. A task facade routes side-effect requests to the custodian and receives immutable observations. VM execution stays single-owner. CPU-bound pure Lua can use separately owned worker VMs only if they have no direct retained/context access.
3. **Explicit durable segments.** A retained segment contains named entrypoint, immutable input/state, generation, selected dependencies, logical child/effect identities and continuation disposition. Resume invokes that entrypoint against that retained state. Supported native APIs must resolve recorded logical identities. Segment commits batch next-state/child-admission decisions; external effects begin only after durable admission. Lost uncheckpointed code is visible, not silently replayed.
4. **Executor adapters, independent authority.** Adapt existing Participants and CommandJobs; add task-local model/tool/Lua and remote executors as actual capability units. Executor handles carry environment/incarnation/lease fencing. The scheduler decides eligibility; executor observes actual process/provider lifecycle. A surviving supervisor can be added without moving authority into the terminal or adopting unrelated services.
5. **Structured scopes with separate observation joins.** Define all/any/quorum over declared outcome predicates. Selection records exact member set and chosen result identities. Timeout, readiness, child termination and retained scope settlement differ. Loser disposition is explicit: cancel-and-settle, continue owned in scope, or transfer to another named scope. Existing participant seal/join cannot stand in for every variant.
6. **Explicit context and workspace publication.** Concurrent workers read immutable selected context and operate on owned workspace leases. Parent context imports results at named durable boundaries with provenance; source integration is a separately admitted merge/checkpoint effect. A shared checkout must have declared ownership/conflict rules. Candidate pool can furnish leases/artifacts; it does not decide workflow completion.
7. **Events/timers using same admitted decisions.** Generalize station adapter admission into a durable native inbox with stable source identity/content digest, checkpointed consumption and defined retention/dedup horizons. Event receipt/admission/consumption/acknowledgement differ. Timer is a retained wait with restart mapping policy; a timer thread waking is an observation, not automatically permission to dispatch.
8. **Audit and performance integrated at native boundaries.** Preserve the approved raw hook→retained memory→recorder→tertiary architecture. Add fields/sites for actual workflow owners/admission/control/dispatch/settlement; do not process raw records to run the scheduler. Measure end-to-end owner latency, admitted throughput, queue pressure, fairness, restoration cost and capture volume as separate claims. No generic latency claim follows from emitter microbenchmarks.

## Fault oracles already worth extending

- [participants_test](../../tests/participants_test.cpp) directly gates two transports and checks simultaneous live requests; refuses capacity before third admission; checks message dedup/conflicts, queue limits, cancelled undispatched directions, preserved unknowns, save-before-launch and zero replay on restore.
- [participants_raw_test](../../tests/participants_raw_test.cpp) checks acquired original byte ranges/disk preservation, overflow, native cancellation endpoint ownership, source admission and post-ack allocation failures. These are actual original/custody fault classes, independent of presentation snapshots.
- [retained_state_crash_test](../../tests/retained_state_crash_test.cpp#L248) SIGKILLs around effect dispatch and independently reads effect bytes; checks old identity never dispatches after recovery and explicit new retry does. Extend crash cuts to segment decision, child dispatch, result capture and continuation commit.
- [participant_recovery_test](../../tests/participant_recovery_test.cpp) verifies unresolved participant start can reopen unknown without provider call while unresolved exec refuses ordinary recovery.
- [workflows_test](../../tests/workflows_test.cpp), [program_workflow_raw_test](../../tests/program_workflow_raw_test.cpp) check selector collisions, ambiguity, exact invocation arguments, same-turn parked protocol, staged-definition success/failure/cancel activation, limits, source/original association and failure after acknowledged publication. Extend to root-generation ancestry and unaffected-root progress.
- [command_jobs_engine_test](../../tests/command_jobs_engine_test.cpp) uses real child markers, PID, exact binary output and PTY input; checks one launch across waits, no renewed deadline, native input admission, capture pressure, command progress during quiet provider calls, and shutdown. Extend to generalized executor custody, late controls and scope settlement.
- [station_test](../../tests/station_test.cpp), [station_main_native_test](../../tests/station_main_native_test.py) attack source dedup, controls, pause/reopen and real session behavior. Replace source-owned pending snapshot with actual durable inbox only when its new admission/consumption oracle exists.
- [saved_state_test](../../tests/saved_state_test.cpp), [retained_state_test](../../tests/retained_state_test.cpp) exercise derived recovery/index/original mechanics. Waiting-run restart needs exact retained run/wait restoration and independent zero-repeat external effect counts; reopening speed alone is insufficient.

Use a small independent transition model/deterministic simulator for scheduler interleavings (joins/cancel/deadlines/late observations/authority changes), real process crashes for dispatch uncertainty, real native process/PTTY fixtures for custody, and exact retained bytes for publication. These attack distinct fault classes. Do not add another layer that merely certifies the same test's receipts.

## Design questions that cannot remain vague

- Is a root workflow a conversation participant with its own working context, or can several orchestration roots act on one conversation only through explicit serialized context commits? Both can exist, but neither should rely on unchecked labels.
- What can a successful any/quorum join release while losing children still owe local cleanup/original retention? Parent readiness and scope settlement must not be conflated.
- Are durable programs explicit state/entrypoint segments only, or is a syntax/compiler front end allowed to generate those segments? Arbitrary Lua stack serialization is excluded by existing design; transparent replay needs deterministic APIs and stable effect addressing first.
- What happens to a retained but unacknowledged segment decision on recovery? Readable committed batch is authoritative, but caller acknowledgement/dispatch remain distinct.
- How are stable child keys allocated across loops/dynamic fanout and branch changes? Human names alone are insufficient, fresh IDs on reexecution defeat dedup, and input mismatch must conflict.
- Which executor effects support safe retries, external idempotency keys, result lookup, reconciliation, compensation or no automatic continuation? These must be declared adapter capabilities plus exact actual outcome, never inferred from a generic error.
- What is the restart clock policy for each deadline, including downtime? Existing monotonic times are process-domain values and cannot be compared after restart.
- What native authority survives process death/refit, and who independently captures existing workers while the harness rebuilds? An expired heartbeat does not prove a local worker or remote effect stopped.
- How does bounded saved-state recovery retain active workflow closure without loading lifetime history or dropping effect obligations? Current settled-only fast path cannot answer this.
- Which admission/settlement budget moves with scope transfer and remote execution? Mandatory termination/unknown observation must remain fundable during exhaustion.
