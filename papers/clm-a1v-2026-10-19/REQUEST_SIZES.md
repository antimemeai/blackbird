## Caveats

- Wire bytes are the exact JSON body curl sent (site 1301). Blackbird's own `native request bytes` (BBM2 packet,
  stdout logs) run about 5-10% below the wire size for the same conversation (e.g. a-t08-luna last: native 132.4 KiB,
  wire 142.8 KiB; r2-t05-paper last: native 443.9, wire 495.0). Native lines are one per logical request and are not
  joined one-to-one to wire attempts; runs whose requests were retried after 180 s cuts have fewer native lines.
- About 26.6-27.2 KiB of every wire body is fixed: 43 tool schemas (24.7 KiB; 25.3 KiB for paper) plus 1.7 KiB of
  instructions. The first request of a run costs 4.7-5.0k input tokens on luna, 7.1-7.4k on mimo, 6.4-6.7k on paper.
- Input tokens come only from completed streams (HTTP 200 with a `usage` block): 718 of 762 requests. The 31 requests
  cut at 180 s and the 13 ultraspeed HTTP 400s have none. Token counts include tools and instructions.
- Bytes per token differ by provider: luna carries encrypted `reasoning` items in its input, so it has more bytes per
  token (5.7-6.8) than paper (3.4-4.1) or mimo (about 3.6). A byte budget does not translate to the same token budget
  across providers.
- No run ever shrank its request by more than 10% between consecutive attempts: no compaction or reset occurred in
  this campaign, so these numbers are uncompacted conversation growth. Retries after 180 s cuts resend the same body
  (flat runs r-t05-paper, r-t06-mimo, r-t06-paper, r-t07-paper).
- Ordering uses the transport-region begin clock; continued sessions (several raw runs) share the host monotonic clock.
- STREAM_TIMING.md reported 15 requests lacking 1302/1303 records; keyed by the request reference in the 1302 record,
  this pass found an HTTP 200 status and a usage block for every one of them. The difference is in the record keying;
  it does not affect sizes.
- "largest input item bytes" is a compact re-serialisation of each item, so it is approximate; the input-array span
  itself is exact.
