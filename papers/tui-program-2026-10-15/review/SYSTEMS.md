# Integrated TUI design challenge: systems boundaries

2026-10-15. One bounded integrated design challenge over `docs/TUI_DOCTRINE.md`, `TUI_COMPONENTS.md`, `TUI_VIEWS.md`, `TUI_IMPLEMENTATION_PLAN.md`, `TUI_METRICS_VIEWS.md` and `TUI_EXISTING_VIEWS.md`. Findings concern integration mechanisms, not a review of earlier reports. No production changes, runtime experiments, source tests or assurance campaign were performed. Locations refer to the documents read during this pass.

## P1 — Composition purity has no native admission mechanism

**Location:** `docs/TUI_COMPONENTS.md:58–68`, particularly the generic async request operation and asynchronous domain access; `docs/TUI_IMPLEMENTATION_PLAN.md:60–66`, exposing async query/action requests in the UI VM. This conflicts with the required behavior in `docs/TUI_DOCTRINE.md:49–50` and the effects prohibition in the component ownership table.

**Failure:** The same composition VM constructs a view, handles local events and can submit asynchronous domain work. The contracts say measurement/painting must not execute effects, but do not specify how native admission distinguishes a rebuild from a deliberate action handler. An ordinary composition function could call the effectful async request API every time a source revision invalidates it. Native execution occurring later on a different thread does not make the originating operation effect-free. A failed scene candidate can therefore launch work on every refresh while the last good scene remains visible.

**Direct fix:** Define native call phases and enforce them at the action bridge before queue acceptance. Composition/measure/paint and display-preview phases can build descriptions and request permitted read-only resources; effectful dispatch is available only in an explicit identified action-handler/operation phase. Distinguish an effectful action request from a read-only resource query in the API and validation. Reload/validation must not manufacture an action phase. This preserves programmability through ordinary actions and owned operations without making rendering itself an implicit effect trigger. Unit2 acceptance should directly verify that a composition/preview attempt to dispatch an effect is rejected before any owner admission.

## P1 — Scene publication does not resolve queued coordinate events

**Location:** `docs/TUI_COMPONENTS.md:48` publishes geometry and bindings together; `:92` maps mouse input to a completely emitted frame; `:133–137` permits scene acceptance while output drains. `docs/TUI_DOCTRINE.md:93–97` requires changes not silently to transfer an action to another object.

**Failure:** A mouse event can be acquired under scene A and wait in an input/gesture queue while frame B completes. If dispatch later looks up the current completely emitted geometry, the same coordinate can address a different still-valid object B. Domain identity/revision checks do not catch this: the request can validly act on B even though the initiating gesture referred to A. Capturing an event under A but retaining only raw coordinates loses the needed relation. Separately, a PTY mouse report carries no screen-frame identifier, so the host must not assume that the latest byte completion identifies what the terminal had displayed when the user clicked.

**Direct fix:** Capture the acquisition-time scene/geometry revision and resolved local/domain target with the event; keep them through gesture resolution and dispatch. A later scene must not reinterpret the queued coordinate. Specify a conservative policy when geometry is transitioning or the input cannot be attributed to a stable frame: preserve a local selection/inspection interaction or reject the effectful coordinate gesture rather than resolving it against a new row. State the remaining terminal-display limitation honestly. Add one direct Unit1 case acquiring a coordinate gesture under A, publishing/reordering B before dispatch, and requiring the original target or explicit refusal, never B. No automatic confirmation gate is needed.

## P2 — The action bridge lacks an invocation identity and ambiguous-delivery rule

**Location:** `docs/TUI_COMPONENTS.md:61–64` defines action definitions/handlers; `:76` distinguishes queue acceptance/refusal; `:143–147` separates view lifetime from effects. `docs/TUI_IMPLEMENTATION_PLAN.md:81–85` compares human/model/Lua references, but does not state the new bridge's delivery semantics.

**Failure:** An action definition identity is not the identity of one invocation. A handler can submit an action, fail before receiving acknowledgment, and then be rerun after composition reload or a view reconnection. The owner may already have admitted the first effect. Without a retained invocation/origin key or an explicit unknown disposition, retrying the UI request can create a second effect under a new runtime attempt. Conversely, deduplicating solely by action ID would incorrectly suppress two deliberate invocations. Existing domain operation contracts help only if the bridge carries their identities correctly.

**Direct fix:** Specify an owned action envelope with a fresh invocation identity for each deliberate trigger, origin event/handler generation, target and relevant input revision. Retain this identity across queue submission/acknowledgment and pass it into the existing owner's supported operation-key mechanism. If a domain lacks safe duplicate reconciliation, ambiguous delivery stays unknown and is queried/reconciled rather than automatically repeated. A deliberate retry remains a new explicit attempt. Unit2 needs one direct case where the owner accepts but acknowledgment is withheld, followed by a handler/view restart; there must be one effect or an honest unresolved state, not an automatic duplicate. This adds no second authoritative operation ledger.

## Boundaries that did not produce findings

The metrics documents explicitly preserve raw producer → separate recorder → tertiary transformation, bound examined work separately from returned records, preserve missing/unknown values and source prefixes, and avoid claiming byte completion is physical paint. The plan keeps broad external adapters, live native-host attachment, full tool-using teams and actual evaluation execution separate from delivered component capability. This pass found no additional substantive producer/consumer or current-capability misstatement requiring a change.
